# Updater integration audit — 2026-10-11

Read-only audit before and after updater integration. No source or tests were changed or run for this report. Evidence: `delivery-readiness.md`, `lib/services/app_update_service.dart`, `lib/core/app_update_ui_copy.dart`, `lib/core/app_update_policy.dart`, updater consumers, and `test/services/app_update_service_test.dart`. The first three sections record the initial risks; the final review below records their current disposition.

## Highest-priority boundary: release data must match the policy target

The delivery inventory shows the local deployment identifying as **1.1.46** while the latest published GitHub Release is **v1.1.43**. Before integration, `_fillMissingDisplayDataFromGitHub()` asked GitHub to fill any missing version, notes, or URL, even when the release tag differed from the loaded backend version. A policy for 1.1.46 with a missing APK URL could therefore have displayed or installed a 1.1.43 release asset.

For an already selected backend target, fill notes or APK URL only when the release tag equals the full target after removing an optional leading `v`; use the same target for the asset. Do not attach a different release's body to that target. Keep the server's force-update switch, minimum version/build, blocked reason, latest version/build, and URL authority intact. Where the backend has no target version, GitHub may remain the existing fallback source; where the backend supplies only a build code for the same version name, do not infer that an arbitrary GitHub APK represents that newer build. The existing stale-URL sanitizer should still reject URLs that clearly name an older version. Prefer an honest missing-package state over a mismatched APK.

## Release notes provenance and live locale

Before integration, `_latestNotes` stored backend `update_notes` / `release_notes` and GitHub `body`, but also received app-generated fallback text during checks and downloaded-installer restore. The service now keeps that field for authored release body only. `latestNotesForDisplay` returns a nonempty authored body as supplied and lazily selects factual localized fallback copy when no body exists.

The service uses `_authoredText` to detect blank or non-string values while retaining nonblank supplied whitespace (`app_update_service.dart:425-427`). It keeps `formatUpdateNotesForDisplay()` in `lib/core/app_update_policy.dart` and `debugFormatReleaseNotesForTest()` as standalone compatibility behavior. New service tests assert literal body preservation and honest localized fallback.

The mobile update dialog already rebuilds via `I18n.localeListenable` (`lib/screens/mine_screen.dart:628-696`). The force gate watches `AppUpdateService` but its surrounding labels are currently Chinese (`lib/widgets/force_update_gate.dart:53-180`); a service locale listener can refresh only the service-provided notes/error, so page-owned copy remains a separate boundary. If adding a listener in `AppUpdateService`, remove it in `dispose()` and notify after `I18n.current` changes. A locale change should not launch a check, modify release metadata, alter `hasUpdate`/`mustUpdate`, or reset download progress.

## Error provenance and restore edges

Before integration, `_error` stored rendered text from check, GitHub, permission, platform, and installer failures, including raw interpolated installer exceptions. The current service stores typed `AppUpdateNotice` values and renders through `userVisibleApiError` with a localized safe fallback. `AppUpdateInstaller.downloadApk()` may throw an `HttpException` carrying the download URL (`lib/services/app_update_installer_io.dart:19-64`), and platform exceptions can contain implementation details; the new copy path suppresses those raw details.

Preserve the distinct 404 “no Release yet” and non-200 GitHub states rather than replacing them with a generic success. `checkNow()` catches network/backend failures and then restores a previously downloaded installer, clearing the error if one remains (`app_update_service.dart:156-159`); `checkServerPolicyNow()` does the same (`:208-211`). This offline installer path must continue to expose a valid cached APK and its version/build/URL without storing localized notes. `_restoreDownloadedInstaller(allowPopulateUpdateInfo: false)` must still reject a cache that disagrees with the newly loaded target (`:787-886`); `allowPopulateUpdateInfo: true` may repopulate missing target fields but should not fabricate release notes.

Before integration, `_tryInstallDownloadedInstaller()` called `installApk(path)` without a surrounding catch. `downloadAndInstallLatest()` now catches that preflight failure and renders a safe typed notice while retaining the cached file for retry (`app_update_service.dart:950-965`). The permission handoff remains: show the permission-required message, open settings, then let the user retry installation of the downloaded APK.

## Acceptance cases for integration review

1. Backend policy target 1.1.46 with missing notes/URL plus GitHub latest v1.1.43: no v1.1.43 body or APK attaches to 1.1.46; force-update lock and missing-package explanation remain correct.
2. Backend target and GitHub tag match: only missing display data is filled; backend minimum version/build, force switch, blocked reason, and version/build remain authoritative. A stale backend APK URL may be replaced by a matching release asset.
3. Backend or GitHub authored body displays literally in both locales. Missing notes show a factual localized fallback that changes Chinese ↔ English without another network request or cached-field mutation. The standalone summary formatter retains its existing behavior.
4. Backend/API, GitHub 404/non-200, no APK, unsupported platform, install permission, download, and install errors follow the current locale after a switch. Raw URLs, exception classes, and implementation details do not appear in user-facing errors.
5. Offline valid downloaded APK remains installable with correct target metadata and no fabricated release body. A stale/mismatched cached APK remains rejected. Locale changes do not affect `hasUpdate`, `mustUpdate`, installer path, progress, or retry capability.

## Final read-only review of the working tree

The current `AppUpdateService` stores typed `AppUpdateNotice` errors and renders notes and errors on read. It subscribes to `I18n.localeListenable` and removes the listener in `dispose()` (`app_update_service.dart:32-45`). It preserves nonblank authored notes and blocked reasons literally, never writes generated fallback into `_latestNotes`, and restores cached installer facts without inventing release copy (`:75-93,279-301,370-410,786-840`). `lib/core/app_update_ui_copy.dart:164-180` now says only that release notes were not provided; it does not claim unsupplied fixes. Its download/install failure fallback is operation-neutral (`:195-213`) and filters error details through `userVisibleApiError`.

Backend policy remains authoritative when GitHub fills missing display data: the release tag must equal the full selected target after removing only a leading `v`; a different version or prerelease suffix cannot supply notes or URL (`app_update_service.dart:715-735`). `_selectBestApkAsset()` now filters candidates **before ranking** (`:1037-1051`). `_releaseApkMatchesTarget()` requires an HTTP(S) URL with a host and rejects any numeric three-part version token in the asset name or decoded URL path that differs from the target (`:1054-1078`). Its lookahead regex recognizes adjacent versioned path segments. This applies in both standalone GitHub fallback and backend-fill modes. An unversioned generic APK remains eligible.

`test/services/app_update_service_test.dart` now covers literal notes and blocked reasons, locale switches without new requests or changed policy facts, safe typed errors, exact backend/GitHub target matching, mismatched APK names and paths, adjacent versioned path segments, and candidate filtering before ranking. Existing service fixtures now register disposal cleanup; the locale-listener lifecycle case disposes explicitly and checks that later locale changes do not notify it. The tests were being rerun by the root at this review; **this audit did not execute them or claim a pass result**. The standalone `formatUpdateNotesForDisplay()` behavior remains in place for its callers/tests.

**Remaining evidence limit:** filename, URL, and release-tag checks cannot prove the APK's internal version/build, signing identity, or content. The matcher compares numeric three-part tokens; it does not establish prerelease/build suffix provenance for the APK itself, and an unversioned generic APK carries no version evidence. A same-version name also does not prove a same-build binary. Do not treat this source audit or GitHub metadata as APK manifest/signature verification. No confirmed implementation defect remains within this updater integration diff from the read-only review.
