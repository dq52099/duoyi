# Widget final UX contract — 2026-10-11

Scope: read-only source review of widget sizing, rendering, publication, preview, and the existing Calendar deep-link handler. This is a decision record, not device acceptance. No production source was changed; no tests, builds, Flutter commands, or devices were run.

## Decision 1: standard 3×2 preview and bottom navigation

**Keep the native Android height rule and correct the previews.** The standard provider requests 180×110dp and 3×2 cells (`android/app/src/main/res/xml/duoyi_calendar_widget_info.xml:2–10`; the other kinds use the same profile). A widget remains in effective `standard` mode at 180×110dp (`DuoyiWidgetFrameCore.kt:71–79`), but the final renderer hides its bottom navigation at heights of 149dp or less for all ten layouts (`DuoyiWidgetSnapshot.kt:124–145`). Thus the nominal standard widget has no bottom bar. The bar can appear when a resizable standard widget has at least 150dp of launcher height; detailed 250×180dp can show it.

The Flutter sample currently labels standard as `3x2` with a 1.5 aspect ratio and shows a bottom bar for every noncompact sample (`lib/screens/widget_screen.dart:858–866, 1500–1519`). Android's standard launcher `previewLayout` also draws a fixed 26dp bar (`android/app/src/main/res/layout/duoyi_widget_preview_standard.xml:40–50`). Both imply a control unavailable at nominal 3×2 height. For Android, show the standard sample and launcher preview without the bar; show it in the detailed sample, and explain or depict that a taller resized standard widget may gain it. If the Flutter sample is shared across platforms, gate that rule by platform: the iOS medium widget intentionally renders its footer, while small does not (`ios/DuoyiWidgets/DuoyiWidgets.swift:1582–1611`). An Android-specific 180:110 sample ratio would also better represent the nominal provider bounds.

Preserve the current iOS-style visual treatment and the native 110dp request. Raising the Android minimum height or forcing a four-tab bar into 110dp would consume space reserved for the widget's primary content and actions. This is a preview accuracy repair, not a functional reason to change the widget size.

## Decision 2: calendar day taps

**Keep the grid tap defined as “open Calendar.”** The Android month grid is one `TextView` (`android/app/src/main/res/layout/duoyi_calendar_widget.xml:103–115`), and its grid, month, title, and today affordances share `duoyi://tab/calendar` (`DuoyiCalendarWidgetProvider.kt:151–169`). The Flutter handler maps `duoyi://tab/calendar` to tab 3 and maps `duoyi://calendar` to the same tab; neither branch reads a date path or query parameter (`lib/main.dart:4032–4094`). The native Calendar event-target validator accepts the bare Calendar host and rejects a Calendar path (`DuoyiWidgetContent.kt:265–291`). There is no existing date-specific widget deep-link contract to reuse.

Day selection would be a separate feature: define and consume a date URI in Flutter, represent days as distinct native tap targets with appropriate bounds, and preserve the Calendar-root fallback. Do not add a date-looking URL to the current single text grid; it would suggest precision that the target cannot deliver. The current root navigation is functional.

## Decision 3: cleared account and empty data copy

**Use neutral guidance for unpublished or cleared data; do not tell the user to sign in.** Native freshness requires a valid snapshot day, offset, and nonblank account nonce (`DuoyiWidgetFrameCore.kt:37–45`). Account clearing writes an empty snapshot day, default values, and a new nonblank nonce (`lib/services/home_widget_service.dart:341–381`). The renderer replaces any nonfresh daily content with generic pending-refresh strings and zero counters (`DuoyiWidgetRenderFrame.kt:27–61`; `DuoyiWidgetCopy.kt:38–91`). A legitimate fresh, empty publication instead retains its normal localized empty-state values (`home_widget_service.dart:47–115, 561–718`), so an empty count alone must never trigger a sign-in prompt.

The canonical native publication document carries `published`, `cleared`, or `blocked`. Current `toFlatValues()` exposes `widget_publication_state` alongside the account, locale, day, and offset (`DuoyiWidgetPublicationDocument.kt:37–43`), and `DuoyiWidgetFrameCore` already reads that state and trusts only a published session. `DuoyiWidgetRenderFrame` still uses the same pending-refresh projection for all nonfresh states. The earlier description that render values omit publication state is superseded by this source check. More importantly, `cleared` is a tombstone created when a workspace opens or is invalidated, including guest workspaces (`DuoyiWidgetPublicationTransition.kt:171–186, 233–237`; `lib/main.dart:2363–2380`). It is not an authentication claim. The legacy flat payload likewise has no signed-out marker (`home_widget_service.dart:47–52, 370–376`).

For a bounded copy polish, use the already exposed canonical publication state to select neutral cleared/blocked/absent guidance such as **“Open Duoyi to update this widget” / “打开多仪以更新小组件”**. Keep “data pending refresh” for a previously published but old snapshot, and keep the normal “no items yet” copy for a fresh empty publication. An actual sign-in prompt would require an explicit, trustworthy account-state publication contract. It would be especially misleading for the supported guest/local workspace (`lib/main.dart:2363–2380`).

## Priority assessment

None of these three source-level gaps blocks the existing core flows: all ten kinds can render their main content and actions, Calendar opens its destination, and clearing removes prior account content. The standard preview is materially misleading and should be corrected before describing 3×2 behavior as polished. Date-specific taps are an optional added feature. Cleared-state copy is a bounded clarity improvement. Source inspection cannot establish launcher acceptance, resize behavior on OEM launchers, action delivery, or real rendered legibility; that device-level acceptance remains open as recorded in `widget-feature-final-inventory-20261011.md`.
