# Todo schedule-for-today account fence — review contract (2026-10-11)

Read-only pre-patch review of `TodoProvider.scheduleTodoForToday`, `AccountLocalDataCleaner`, and relevant provider tests. The repo and workspace `AGENTS.md` files were read. No production or test files were edited; no tests or builds were run for this review.

## Existing race

`lib/screens/today_screen.dart:359-371` passes a suggestion's Todo ID to `scheduleTodoForToday`. At `lib/providers/todo_provider.dart:1468-1508`, the public method claims that ID and `_scheduleTodoForTodayLocked` awaits `_ensureStorageLoaded()` before looking it up. No origin account/storage generation is checked after that await. `resetLocalState` increments `_storageGeneration`, clears `_todos`, and starts fresh hydration, but leaves both in-flight ID sets intact (`todo_provider.dart:368-382`). `AccountLocalDataCleaner.invalidateInFlightAccountWrites()` synchronously increments its global account generation (`lib/services/account_local_data_cleaner.dart:18-32`). If a new account has the same ID when the old await resumes, the old action can mutate its item.

## Fence placement

1. At public method entry, capture `_storageGeneration` and `AccountLocalDataCleaner.accountDataGeneration` before the first await. An optional `expectedAccountDataGeneration` supplied by the caller must be compared to the current account generation **before either in-flight claim**; a stale callback returns `false` without reserving an ID.
2. Pass the two captured values unchanged to `_scheduleTodoForTodayLocked`. Check `_isCurrentStorageGeneration(originStorage, originAccount)` immediately after `_ensureStorageLoaded()` and before `_todos.indexWhere` or any mutation.
3. After `await _saveToStorage()`, check the same origins before `_notify()`. `_saveToStorage` can itself await hydration/write callbacks; a stale return does not prove that the action still belongs to the active account.
4. Check again after synchronous `_notify()`: its listeners run synchronously and can invalidate the account or call `resetLocalState`. Only then start reminder sync. Check after awaited reminder sync before returning `true`. In the no-wait branch, a synchronous scheduler callback can also change account state before the async sync returns, so recheck after launching the unawaited call and before returning `true`.
5. Retain unconditional removal of **both** `_inFlightScheduleTodayTodoIds` and `_inFlightTodoMutationIds` in the public `finally` (`todo_provider.dart:1493-1497`). `resetLocalState` does not clear either set. Epoch-guarding cleanup would leak old claims and block a same-ID action in the next account. Duplicate/no-claim early exits still remove only the claim actually acquired.

`_syncTodoRemindersNow` captures its own storage and account generation and suppresses stale result application (`todo_provider.dart:559-685`). The schedule method still needs its own checks before invoking that sync and before reporting success. A Today caller should capture the expected account generation when the old suggestion callback is created, pass it to the public method, and suppress stale snackbar feedback after await. Capturing an expected generation only at tap time cannot distinguish an old retained callback from a new account action.

## Required scenarios for the patch owner

- Gate hydration, start an old account schedule action, switch account/reset, hydrate a new Todo with the **same ID**, release the gate: old future returns `false`; new in-memory item, persisted JSON, revision, notification count, and reminder calls are unchanged by the old action.
- Call with a stale explicit `expectedAccountDataGeneration` after a switch: return `false` without claiming either ID set. With no older same-ID action still in flight, a current-epoch request must proceed; if an older action still owns the claim, it can proceed after that action's unconditional cleanup.
- Invalidate/reset during save: suppress the stale `_notify`, reminder launch, and `true` result. The new account snapshot must remain intact.
- Make a provider listener reset the account synchronously from `_notify`: the old action must not schedule reminders or return `true` after that callback.
- Hold awaited reminder sync, then switch account: result becomes `false` and stale reminder status is not applied. Also exercise `waitForReminderSync: false` with a synchronous scheduler callback that switches account.
- Verify ordinary schedule-today behavior, no-wait behavior, duplicate in-flight suppression, and final claim cleanup after stale completion. A fresh same-ID action should work once the old action finishes. Existing disposal/duplicate tests (`test/providers/todo_provider_disposal_test.dart`, `test/providers/todo_batch_operations_test.dart`) should retain their current behavior.

This section records the pre-patch review contract; the post-patch audit follows.

## Post-patch static review (2026-10-11)

The uncommitted provider patch now captures storage and account generations before claims, rejects a stale explicit origin, checks after initial hydration, after save, after synchronous notification, and after reminder sync, and retains unconditional cleanup of both claim sets. The ten new provider tests exercise the listed hydration, reset, disposal, callback, reminder, and normal-operation paths. This is a source review only; I did not run tests or builds.

**Open save-queue race:** `scheduleTodoForToday` checks its origin only *after* `await _saveToStorage()` (`todo_provider.dart:1572-1575`). `_saveToStorage` awaits `_ensureStorageLoaded()` and then calls `_writeToStorage()` (`:508-510`); `_writeToStorage` queues a closure (`:539-545`), and `_writeTodosSnapshot` captures the generation and `_todos` only when that closure executes (`:519-533`). If the account resets after the schedule mutation but while the save waits for hydration or an earlier queued write, the stale schedule write may execute in the new epoch. It can persist the new account's current list, including an empty list before hydration, and call `onLocalMutationPersisted`; the post-save fence then returns `false` too late to prevent that write. Pass the captured origin into the save path, check it after `_ensureStorageLoaded()` and again inside the queued closure before taking a snapshot. Preserve the snapshot's existing checks around `SharedPreferences` access.

The new `reset during persisted callback` test covers a switch *after* the scheduled write has persisted; it does not cover the queued-write interval above. Add a deterministic queued-write gate, reset and install the new account's stored Todo before releasing it, and assert that the old action leaves the new stored value and persistence callback count unchanged. The same-ID hydration test asserts in-memory and stored values and reminder calls, but does not yet assert the revision or notification count named in the pre-patch contract.

**Caller integration remains open:** `today_screen.dart:359-371` still calls `scheduleTodoForToday` without `expectedAccountDataGeneration`. A retained suggestion callback can therefore acquire the new account's generation at tap time. Capture the account generation when that callback is created, pass it to the provider, and suppress stale snackbar feedback after the await. The provider patch should be considered incomplete until the save-queue fence and caller integration are in place.

## Save-queue follow-up review (2026-10-11)

The save-queue finding above is **closed for `scheduleTodoForToday`** by the subsequent uncommitted patch. Its immutable storage/account origins are passed as a `canWrite` closure to `_saveToStorage`. That path checks before and after hydration, then `_writeToStorage` checks before enqueueing and again inside the queued closure, immediately before `_writeTodosSnapshot` begins. The snapshot captures its own current epoch and keeps its existing post-encode and pre-callback checks. There is no asynchronous gap between the queued origin check and the snapshot's initial capture. The old action therefore cannot adopt a new account's epoch and write its list after waiting in the queue. The post-save check still suppresses old notifications, reminder launch, and a `true` result if the account changes during persistence.

The new `stale schedule queued behind a write cannot overwrite the next account` case gates an earlier write's persistence callback, queues schedule-today behind it, resets the account before releasing the gate, and verifies that the unhydrated new account's persisted JSON and callback count are unchanged by the stale schedule. It also checks that a fresh same-ID action succeeds after the old claim is released. The hydration case now checks revision and notification count. The existing final five-file regression log at `.dart_tool/task-temp-20261011/todo-schedule-account-final-regression-20261011.log` lists the new case and ends `+51: All tests passed!`; the patch owner reports exit code 0. I inspected that log and source only; I did not run tests or builds. The focused analysis log was still in progress at this review point, so this section makes no analyzer claim.

The Today UI callback remains a separate open integration item until its creation-time account generation is passed to `scheduleTodoForToday` and stale snackbar feedback is suppressed. This follow-up closes the specific queued-write finding, not that caller item.
