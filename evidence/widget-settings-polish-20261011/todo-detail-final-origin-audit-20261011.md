# Todo detail final origin audit — 2026-10-11

Read-only consequence audit at HEAD `cf4ed63` with the finished uncommitted Todo detail draft. I read both workspace/repo `AGENTS.md` files, the opening-origin test and the relevant Today/Search call paths. No production, test, or Git state was changed; no Flutter command was run.

## Release blockers

1. **Route origin is still late for normal callers.** `TodoDetailScreen.accountGeneration` is optional and `initState` falls back to the *then-current* generation (`todo_detail_screen.dart:48-53,97-105`). Today creates the route at `today_detail_router.dart:53,84-88`, and Search creates its route at `search_screen.dart:92-100`; neither passes a captured generation. Thus `Navigator.push` may be initiated under account A, account B may become current before the detail widget's first `initState`, and the old route will bind to B. If B has the same Todo ID, `_load()` reads B's Todo and editing is enabled. Capture the generation before route creation in Today/Search (and the two direct Todo-screen constructors at `todo_screen.dart:2768,3840`) and pass it into `TodoDetailScreen`; retain the optional fallback only for callers that cannot supply an opening origin. Add a route-created/before-first-frame switch case. The existing `todo_detail_account_origin_test.dart` switches only after the detail has mounted and a draft has been entered.

2. **An invalidated mounted route still displays its old draft.** The account listener bumps operation sequences and disables editing but does not clear `_todo` or the text controllers (`todo_detail_screen.dart:108-120`). The build returns the missing state only if `_missingTodo` is true, or if a *current* route cannot find its Todo (`:932-967`). A now-stale route with `_missingTodo == false` continues to render the old title, notes, attachments, and other draft fields with `canEdit == false` (`:968-1065`). This fails the contract to invalidate old account drafts and may expose old account content over the new session. Render a stale/unavailable state or clear the old draft when the generation changes; do not hydrate a same-ID B item into this route. The current test checks only that B's title was not overwritten.

3. **Subtask mutation can cross the hydration boundary before the UI guard.** Detail `_addSubtask`, `_toggleSubtask`, and `_deleteSubtask` check the route origin before calling the provider and after awaiting it (`todo_detail_screen.dart:539-627`), and their sequence-guarded `finally` blocks correctly avoid clearing a newer operation. But provider `addSubtask`/`toggleSubtask`/`deleteSubtask` enter locked methods that await `_ensureStorageLoaded()` *without* an origin captured and checked before the same-ID lookup (`todo_provider.dart:1832-1998`). If account A starts a subtask action while hydration is pending and B resets/hydrates a Todo with the same ID, the old action can mutate B before Todo detail sees its post-await account check. Add an immutable expected-origin parameter or provider-side captured storage/account generation to those three methods, check after hydration before lookup/mutation, and guard their save queues as needed. A gated same-ID hydration test for add (and toggle/delete with a colliding subtask ID) is the narrow reproduction. This is a provider boundary; a UI-only `finally` change cannot close it.

## Paths that hold, and Today callback edge

`_save` gates entry on the fixed route origin, checks after reminder preflight and provider save, and uses `_saveSeq` so an old completion or `finally` cannot restore a newer save state (`todo_detail_screen.dart:308-487`). The provider update method captures its own generation before its initial hydration await. `_TaskCommentsPanel` receives the route origin, gates send entry/completion, and increments `_sendSeq` on invalidation, so an old response/finally does not clear a new send (`:2475-2650`). Those UI checks do not by themselves cancel an already issued network request or solve provider write-queue races; neither is evidence that an old draft can overwrite B through the reviewed UI path.

Today `reminderSection()` captures `boundAccountGeneration` each time that parent build runs and passes it into `scheduleTodoForToday`, with pre-call and post-await checks (`today_screen.dart:346-385`). An unchanged callback from A is rejected after a switch. The retained `_SuggestionSectionState` has a narrower rebind edge: an old row's `onPressed` captures its old `TodoItem` but calls `_addToday(t)`; `_addToday` reads the *current* `widget.onAddToday` (`:3445-3452,3515-3517`). If the keyed section is rebuilt for B before a retained A button callback is invoked, that old item can be sent to B's freshly bound callback. With a colliding ID, the provider sees B's expected generation and may schedule B's Todo. Bind the action/origin to the row callback that captured the item, or pass an immutable row origin into `_addToday` and reject it before calling the current widget callback. Test by retaining an A button callback, switching/rebuilding to B with the same ID, then invoking the retained callback. The ordinary freshly built B row should still work. `_addingTodoIds` is also ID-only and can temporarily disable B's same-ID row while A's action is pending; clear or version that busy state on account change without letting A's `finally` clear a B operation.

These findings are source conclusions only. The AGY `SUCCESS` status and the existing mounted-draft test do not cover the before-first-frame, stale-visibility, provider-hydration, or retained-button cases above.

## Provider subtask and detail-save boundary follow-up

Read-only source audit; no tests or Flutter commands were run. This section narrows the provider work to the four subtask entry points and `updateTodoWithResult`.

**All four subtask entry points have the same initial race.** `addSubtask`, `toggleSubtask`, `deleteSubtask`, and `reorderSubtasks` claim keys and then enter locked methods that await `_ensureStorageLoaded()` before looking up Todo IDs (`todo_provider.dart:1832-2050`). None captures an account/storage origin before that await. A reset followed by same-ID hydration can make an A action mutate B. Add an optional `expectedAccountDataGeneration` at each public entry for route-bound callers, capture `_storageGeneration` and either that explicit account generation or the current generation before *any* claim, and reject a stale explicit origin before duplicate bookkeeping. Pass both immutable values into the locked method; check after hydration and before Todo/subtask lookup or mutation. The route must pass its `_originAccountGeneration` for add/toggle/delete and for the direct reorder call at `todo_detail_screen.dart:1341`; a provider-only capture cannot identify an A callback invoked after B is already current.

**Every subtask save needs the same queued-write guard as schedule-today.** Add, reorder, and delete-last-subtask call `_saveToStorage()` directly; toggle and delete-with-remaining-subtasks go through `recomputeParent`, which captures a fresh epoch and calls `_saveToStorage()` without `canWrite` (`todo_provider.dart:1859-2048`). Once an A mutation has occurred, a queue blocked by an earlier write can resume after reset; unguarded `_writeTodosSnapshot` then captures B's epoch and list, persisting B's unhydrated empty list or invoking B's persistence callback for A's action. Pass the original `canWrite: () => _isCurrentStorageGeneration(originStorage, originAccount)` through all four paths, including a narrow origin-aware internal recompute path. `recomputeParent` has no other call sites in `lib` or tests; its existing public behavior can remain compatible with optional origin parameters or a private helper. Check after save before `_notify()`. When `_notify()` may synchronously switch accounts, check again before audit/reminder work. In particular, `recomputeParent` can currently reach `_syncTodoRemindersNow()` after such a switch when `autoToggleByChildren` produces no completion/reopen audit, and delete-last-subtask unconditionally starts reminder sync after `_notify()`.

**Keep claim semantics.** `resetLocalState()` increments the epoch and clears Todo data but does not clear `_inFlightSubtaskCreateKeys`, toggle/delete/reorder keys, or `_inFlightTodoMutationIds` (`todo_provider.dart:368-382`). Preserve unconditional `finally` removal of the exact acquired keys on every stale completion. If the second shared mutation claim fails, release the first acquired subtask key before return; preserve add's duplicate-create `StateError` and the other methods' existing duplicate/no-op behavior. No new permission policy belongs in this provider patch: the detail UI's `canEdit` gate remains before dispatch, while the provider origin gate must precede claims and all later side effects. Existing event/notification ordering for successful current-account operations should stay as-is, with only post-await/post-listener origin checks added.

**Detail save has a narrower version of the queued-write risk.** `_updateTodoLocked` already captures storage/account origins before its hydration await and checks before same-ID lookup (`todo_provider.dart:861-879`), so it does not have the initial subtask hydration bug. It then mutates and calls `_saveToStorage()` without `canWrite` (`:883-897`). A reset while this write is queued can make the stale closure snapshot B's list and fire B's persistence callback; the post-save origin check returns `notSaved` only after that damage. Pass its captured origin to `_saveToStorage(canWrite: ...)`, retain the check before `_notify()`, and add a check after `_notify()` before starting reminder sync/audit because listeners run synchronously. This closes the provider side of Todo detail save without changing edit merge semantics.

**Deterministic gates:** (1) gate hydration before each public subtask call, invalidate/reset, install a B Todo with the same parent ID (and same subtask ID for toggle/delete/reorder), release hydration, then assert B memory/JSON/revision/notifications/reminders unchanged by A; a stale explicit origin should not claim keys. (2) Gate an earlier write's `onLocalMutationPersisted`, mutate A through each subtask path or `updateTodoWithResult` so its save queues, reset and install B's unhydrated JSON, release the gate, and assert B JSON and callback count remain untouched; then hydrate B and verify a fresh same-ID action works after A's `finally`. (3) A synchronous provider listener that invalidates/resets during `_notify()` should not cause the old recompute/update path to launch B reminder sync. Existing disposal and duplicate tests cover different boundaries and should keep passing.

## Provider patch review verdict

Read-only review of the subsequent `lib/providers/todo_provider.dart` diff against the boundary above. **No new provider-side blocker found.** The four public subtask methods now capture storage/account generations and reject a stale explicit origin before private or shared claims. Their locked methods check that origin after hydration and before same-ID lookup. Add, delete-last, reorder, and `recomputeParent` pass the origin into the accepted `_saveToStorage(canWrite: ...)` queue guard and check again before notifying. Toggle and delete-with-remaining-subtasks carry the account origin into `recomputeParent`; they call it synchronously after the initial mutation, with no await or callback between the outer storage check and its own storage capture. `recomputeParent` and delete-last check after synchronous `_notify()` before reminder/audit work. The completion/reopen audit order and reminder call sites remain in their previous branches.

`updateTodoWithResult` now uses its captured origin in `canWrite`, checks after save, and rechecks after `_notify()` before reminder/audit. This closes the queued-write and synchronous-listener paths identified for Todo detail save. Private and shared subtask claims still release unconditionally in `finally`; early shared-claim failures still release the first key, and reset does not clear these sets, preserving fresh same-ID work after stale completion. The original duplicate-create exception and other duplicate no-op behavior remain.

This is a provider-layer verdict only. At this review point, `todo_detail_screen.dart` still calls add/toggle/delete/reorder without `expectedAccountDataGeneration`; a retained old-route callback invoked after B is already current could be accepted as B at provider entry. Pass the fixed `_originAccountGeneration` from each detail call site. The separate before-first-frame route capture, stale-draft visibility, and Today retained-button findings above remain open. No test/analyzer/build result is asserted by this source review.
