# Todo external storage gate review — 2026-10-11

Scope: read-only review of `TodoProvider.runExternalStorageUpdate`, the new `_saveToStorage` origin guard, and `test/providers/todo_external_storage_update_test.dart`. The active Backup integration was not inspected. No tests, Flutter commands, builds, or production edits were performed.

## Verdict

**One queue-contract blocker remains.** Already queued writes drain before the external update, and operation errors release the gate. A Todo mutation started after gate reservation but before its body begins can be silently canceled instead of applying to the restored list.

## Finding

### P1 — New mutation in the drain window is dropped

`runExternalStorageUpdate` reserves `_storageLoadFuture` and `_storageWriteQueue` before yielding, but increments `_storageGeneration` only after it has awaited the older write and load tails ([todo_provider.dart:382](/home/ubuntu/duoyi/lib/providers/todo_provider.dart:382), [todo_provider.dart:384](/home/ubuntu/duoyi/lib/providers/todo_provider.dart:384), [todo_provider.dart:390](/home/ubuntu/duoyi/lib/providers/todo_provider.dart:390), [todo_provider.dart:436](/home/ubuntu/duoyi/lib/providers/todo_provider.dart:436)). `addTodoWithResult` captures the old generation before awaiting `_ensureStorageLoaded`; after the gate completes, that check returns `null` without adding the Todo ([todo_provider.dart:809](/home/ubuntu/duoyi/lib/providers/todo_provider.dart:809), [todo_provider.dart:814](/home/ubuntu/duoyi/lib/providers/todo_provider.dart:814), [todo_provider.dart:816](/home/ubuntu/duoyi/lib/providers/todo_provider.dart:816)). Other mutations with an entry-time generation check have the same timing exposure.

Minimal sequence: hold one older Todo write pending; call `runExternalStorageUpdate` so its gate is reserved while it drains that write; call `addTodo` before releasing the older write. The add waits for the gate. Releasing the older write lets the gate increment the storage generation, run the backup operation, and hydrate. The add then sees a stale captured generation and exits. Its `Future<void>` completes without saving or surfacing an error. The existing “new mutation waits” test begins the add only after `started.future` is completed **inside** the external operation, after the generation increment ([todo_external_storage_update_test.dart:112](/home/ubuntu/duoyi/test/providers/todo_external_storage_update_test.dart:112), [todo_external_storage_update_test.dart:117](/home/ubuntu/duoyi/test/providers/todo_external_storage_update_test.dart:117)); it does not cover this window.

Fix contract: distinguish operations started before the gate was reserved from those started afterward. New arrivals during the drain window should wait, capture the post-update generation, and apply to the hydrated list; if cancellation is intended, return a visible canceled result instead of silently succeeding. Add a test with the gate held in its drain phase and a new add submitted before the external operation starts.
