# Empty widget publication contract — 2026-10-11

Scope: read-only source contract for Android widget publication state and copy. No production files were edited; no Git, Flutter, builds, tests, or devices were run.

## Minimal trusted render API

Add one **render-only** flat field, `widget_publication_state`, with the exact strings `published`, `cleared`, or `blocked`. Derive it solely from the already parsed `DuoyiWidgetPublicationDocument.state` in `DuoyiWidgetPublicationDocument.toFlatValues()` (`android/app/src/main/kotlin/com/duoyi/duoyi/DuoyiWidgetPublicationDocument.kt:14–43`). `DuoyiWidgetSnapshot.values()` already takes flat values from `read.envelope?.document` and overlays only launcher display-mode preferences (`DuoyiWidgetSnapshot.kt:30–41`); those preferences must never supply or override the publication state. When there is no valid envelope, omit the field. Do not label an absent, busy, corrupt, or unavailable read as `cleared` or `blocked`.

This field is presentation metadata, outside the canonical 89-value manifest and outside the persisted document. The document parser requires exact document and value key sets, validates the state enum, and requires an empty day and business data for nonpublished states (`DuoyiWidgetPublicationDocument.kt:27–31, 166–203`). The store rejects malformed envelopes and noncanonical JSON before exposing them; successful reads carry `ready` or `sealed` **store status** plus an envelope, while absent and failed reads have no envelope (`DuoyiWidgetPublicationStore.kt:16–41, 148–161`; `DuoyiWidgetPublicationEnvelope.kt:135–170`). Store status is not the document state: `sealed` can contain `cleared` or `blocked`. Do not infer authentication from any of these states. A new guest workspace also starts with a `cleared` tombstone (`DuoyiWidgetPublicationTransition.kt:166–185, 233–237`; `lib/main.dart:2363–2380`).

`DuoyiWidgetFrameCore` should parse the projected state as an exact recognized value and require `published` in `sessionTrusted` alongside the existing valid day, typed offset, and nonce checks (`DuoyiWidgetFrameCore.kt:37–45`). This makes action trust explicit. A published snapshot from a previous day remains `sessionTrusted` but is not `fresh`; `cleared`, `blocked`, absent, and unknown state remain untrusted and nonfresh. Its raw-value comparison already rejects a state-only change with `data_changed` if the new field is present in both captures (`DuoyiWidgetFrameCore.kt:47–68`). `DuoyiWidgetSnapshot.renderWidget()` recomputes `values(latest, ...)`, compares read status, and accepts a canonical envelope under the store lock (`DuoyiWidgetSnapshot.kt:54–91`), so the state used to render is checked again before commit. Keep the state field in raw values, not only in the mutable display projection.

No v1 document/store schema, SQLite channel, Dart publication DTO, Flutter-to-native payload, or preference mirror change is needed. Adding the key to canonical `values`, accepting a caller-supplied state from `SharedPreferences`, or widening the strict parser would weaken this boundary (`DuoyiWidgetPublicationDocument.kt:49–159, 166–203`; `lib/services/widget_publication.dart:35–90, 240–260`). The expected flat-key fixture in `DuoyiWidgetPublicationDocumentTest.kt:870–878` will need the new projected key, while its canonical document/value key counts remain unchanged.

## Copy and state behavior

| Render state | Display contract | Actions |
| --- | --- | --- |
| `published` and fresh, including all zero/empty business values | Existing localized empty-state copy; do not turn zero counts into a sign-in or refresh prompt. | Existing fresh-action rules. |
| `published` but old local day/offset | Existing “data pending refresh” copy. | No entity or mutating widget action from the old snapshot. |
| `cleared` or `blocked` | Neutral guidance such as “Open Duoyi to update this widget” / “打开多仪以更新小组件”; no sign-in claim. | Calendar/section fallback navigation only; no old entity IDs or timer action. |
| No valid document (`absent`, busy, corrupt, unavailable, unsupported) | The same neutral guidance without inventing a publication state; retain safe locale fallback. | Safe root navigation only. |

`DuoyiWidgetRenderFrame.displayValues()` currently replaces every nonfresh daily field with stale copy, blanks IDs, and zeros counters (`DuoyiWidgetRenderFrame.kt:27–61`). Branch on trusted projected state: retain that masking for every nonfresh frame, but select neutral first-row/summary copy for unpublished or no-document frames, and stale copy only for old `published` frames. The `fresh` branch must remain unchanged. `DuoyiWidgetCopy.staleMessage()` and the refresh control's content description currently say “pending refresh” for all nonfresh frames (`DuoyiWidgetCopy.kt:38–84`; `DuoyiWidgetSnapshot.kt:190–200`); add neutral copy/description selection without weakening freshness checks. Preserve localized blank secondary rows so an empty publication cannot look like real items.

There are provider-specific paths outside `RenderFrame` that also bypass the proposed neutral message: Calendar's stale summary and Anniversary's stale item are synthesized from `isFresh` inside `DuoyiWidgetContent.resolveCalendarSummaryAndTarget()` and `resolveAnniversaryItems()` (`DuoyiWidgetContent.kt:199–215, 315–331`; providers at `DuoyiCalendarWidgetProvider.kt:116–134`, `DuoyiAnniversaryWidgetProvider.kt:76–85`). Focus's untrusted timer caption, summary, and quick-start label are generated in `DuoyiWidgetCopy.kt:126–170, 212–220` through `DuoyiFocusHabitWidgetProvider.kt:103–173`. These paths need the same clear/absent versus old-published distinction, or they will still show “pending refresh” on a cleared widget. Keep the shared logic central and pass the frame's display state where needed.

## Final backend source acceptance — 2026-10-11

The five changed paths now match the backend contract by source inspection. `DuoyiWidgetPublicationDocument.toFlatValues()` projects `widget_publication_state` from its parsed enum without adding it to canonical `values` (`DuoyiWidgetPublicationDocument.kt:37–45`). `DuoyiWidgetFrameCore` recognizes only an exact enum wire string and requires `PUBLISHED` alongside the existing day, typed offset, and nonce for `sessionTrusted` (`DuoyiWidgetFrameCore.kt:36–48`). No extra package import is needed: the enum class is in the same Kotlin package, and `State.entries` was already used by the document parser. The unchanged `DuoyiWidgetSnapshot.values()` reads only the validated document projection and overlays only display-mode preferences, so the new state cannot come from preferences (`DuoyiWidgetSnapshot.kt:30–41`). The unchanged frame recheck compares the projected state in `rawValues`, and the canonical envelope is accepted under the store read lock (`DuoyiWidgetFrameCore.kt:50–68`; `DuoyiWidgetSnapshot.kt:63–91`).

Old published snapshots still have `sessionTrusted == true` when their day/offset/nonce are valid, so existing timer trust and timer-expiry rejection remain; they have `fresh == false` on an old day or offset, so entity and mutating actions remain gated (`DuoyiWidgetFrameCore.kt:43–48, 65–68`; `DuoyiWidgetSnapshot.kt:99–121`). A fresh published document with zero or empty business values remains fresh because counts do not enter the trust predicate, and `DuoyiWidgetRenderFrame` leaves its empty-state values untouched (`DuoyiWidgetRenderFrame.kt:38–61`). Cleared, blocked, missing, and invalid states cannot make a frame fresh. The updated document tests assert all three projected states and the new flat-key set; FrameCore tests cover exact-state trust and state-only rejection; the FrozenPreferences fixture includes published metadata (`DuoyiWidgetPublicationDocumentTest.kt:73–78, 482–490, 870–880`; `DuoyiWidgetFrameCoreTest.kt:111–132, 398–412`; `DuoyiFrozenWidgetPreferencesTest.kt:295–306`).

**Source verdict:** the backend adapter is ready for contract acceptance, subject to the independent pure JVM run already in progress. It does not yet implement neutral clear/absent presentation; the RenderFrame/Copy/Content/provider and preview work remains a separate, pending frontend change. Full Android rendering and device acceptance remain open. No tests or builds were run for this source check.
