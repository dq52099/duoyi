No source, tests, browser probe, package install, or commit was made here. The browser team owns the screenshots. ## What the bundled font can render

`pubspec.yaml:126-129` declares `assets/fonts/DroidSansFallbackFull.ttf` under Flutter family alias `DroidSansFallbackFull`. Its internal font name is **Droid Sans Fallback / Regular**; the different internal name does not invalidate Flutter's declared alias. `fc-scan` and a read-only fontTools cmap inspection of the accepted-head file found 4,033,420 bytes, 28,601 mapped code points, and 20,902 mapped code points in U+4E00–U+9FFF. All sampled Chinese characters in `多仪今日待办日历习惯设置` are present. By contrast, the file maps **0/10 ASCII digits**, **0/26 ASCII uppercase**, and **0/26 ASCII lowercase**; among sampled ASCII punctuation, only space is mapped. Thus this is a real CJK fallback, not a complete Latin/numeric font.

Accepted-head `lib/core/app_brand.dart:6-15,68-83,957-962` sets `sans-serif` as primary and lists platform CJK families before the bundled `DroidSansFallbackFull` last in `fontFamilyFallback`, both in text styles and ThemeData branches. The font is declared and referenced; the source does not accidentally omit the CJK fallback. The accepted-head static test `test/core/web_cjk_font_static_test.dart` checks these declarations and asset presence, but does not check Latin/digit cmap or CanvasKit rendering. Screenshot test support explicitly loads an additional local Latin face (`test/screens/app_ui_upgrade_test.dart:633-655`), so its readable test captures cannot prove the production Web stack has offline Latin coverage.

## Interpreting the controlled browser evidence

The browser probe record `.dart_tool/task-temp-20261011/accepted-head-browser-canvas-local-verified-20261011.json` shows HTTP 200 for the app, one Flutter view and one canvas at both 390×844 and 1440×900, `document.readyState=complete`, `document.fonts.status=loaded`, and screenshots after roughly 12.3 and 11.5 seconds. It records **23/34 intentionally blocked** `fonts.gstatic.com` requests (Roboto and Noto Sans SC) for mobile/desktop. Root's inspection of those screenshots found most Chinese labels readable while some numeric dates, counts, and Latin-like characters appear as square tofu. That pattern is consistent with the bundled CJK-only font covering Chinese while the blocked external Latin/Roboto path leaves ASCII glyphs unresolved in this CanvasKit environment. It is **not** evidence that all Chinese glyphs fail.

An incomplete initial Flutter bootstrap is less consistent with the recorded ready state, mounted CanvasKit view, and elapsed time. `document.fonts.status` alone does not prove CanvasKit's internal font resolution completed, and a local asset GET 200 alone does not prove every text run selected that face. The metadata and controlled screenshot pattern support an **offline Latin/numeric coverage or selection gap**, but do not isolate the exact CanvasKit fallback decision. Deliberate network blocking is a condition of this probe, not a production outage finding.

For AGY's frontend/font ownership, bundle a small licensed Latin face with digits and punctuation as a declared local Flutter family, then put it before the CJK-only font in the app theme's effective font selection (or use one bundled face that covers both ranges). Retain the existing CJK fallback and visual metrics as far as possible. The browser owner can compare the same accepted build with external fonts allowed versus blocked and, after a focused font change, inspect numeric dates/counts and Chinese labels at mobile and desktop sizes. Confirm the selected font and loaded glyphs rather than relying solely on asset GET or `document.fonts.status`. No source change or browser rerun is part of this audit.
