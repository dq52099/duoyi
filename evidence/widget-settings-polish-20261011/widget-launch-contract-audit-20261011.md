## Minimum strict Android launch API

Use one app-owned native entry path for widget Intents. On `onCreate`, capture the launch Intent before `super.onCreate`; on every `onNewIntent`, capture the **new** Intent and call `setIntent(intent)` before `super.onNewIntent` so any plugin observer sees the same received data. Accept only `HOME_WIDGET_LAUNCH_ACTION` with a parseable `duoyi` URI. Allocate one random `widget_delivery` ID per received Intent, store it with the original URI in an ordered, process-owned pending queue, and never derive it from the URI or from a widget snapshot. Replace every incoming `source`/`widget_delivery` occurrence if using query parameters; repeated query keys otherwise parse ambiguously in Dart. Never fill missing day, offset, or account binding with current values. The Intent action is an origin hint, not authorization: the exported Activity can receive a forged explicit Intent. Account nonce validation remains the authorization gate.

One `duoyi/widget_launch` MethodChannel can provide `subscribe` (enable hot delivery and return the pending snapshot), native `onWidgetLaunch` callbacks, `ack(widget_delivery)`, and `unsubscribe`:

- Dart installs its method handler **before** invoking `subscribe`. Native `subscribe` atomically enables hot callbacks and returns **all unacknowledged** `{widget_delivery, uri}` entries in receipt order without removing them. An Intent received during `subscribe` may be present in both the response and a callback; process it once by ID. Retry `subscribe` to drain pending entries after callback/channel failures. Native queue and subscriber changes must be serialized on the Android main thread or behind one lock. `unsubscribe` retains pending entries and clears the subscriber only if the caller's Activity/engine token still owns it; an old Activity's `onDestroy` must not detach a newly attached subscriber.
- `ack(id)` is idempotent and removes only that ID. Dart keeps distinct **in-flight** and **terminal** ID sets: a duplicate in-flight callback must not ACK the first copy's sole native pending entry; a duplicate of a terminal ID may retry ACK. A new Intent carrying an identical URI receives a different ID and remains a genuine tap. Acknowledge terminal validation rejection, section fallback, or accepted dispatch; do not acknowledge merely because a hot callback arrived. If “accepted” means synchronously inserted into a listened Dart stream, document it as a volatile handoff: `handleDeepLink` only schedules a frame ([main:1054–1058](/home/ubuntu/duoyi/lib/main.dart:1054)). An in-memory queue cannot promise exactly-once mutation across process death, especially while current action handlers start provider writes without awaiting them ([main:4224–4264](/home/ubuntu/duoyi/lib/main.dart:4224), [main:4493–4503](/home/ubuntu/duoyi/lib/main.dart:4493)). Skipping `onCreate` intake when `savedInstanceState != null` avoids recreation replay but can lose an unprocessed event after process death; state that limit explicitly.
- Keep the queue bounded against a forged Intent flood; reject oversized/non-`duoyi` data and surface an explicit overflow status instead of silently treating dropped entries as delivered. Do not log full URIs because `quick_todo` can contain user text. The bridge DTO should carry the ID independently from the URI; if the smallest integration also appends it to `Intent.data`, the native receiver must overwrite it and Dart must retain it through `_pendingWidgetUris` and action dispatch until deduplication is complete. Its plugin extras alone would be invisible to the existing `home_widget` plugin, which reads only data. The delivery ID is never an account authorization credential.
- Remove Android consumption of both `HomeWidget.widgetClicked` and `initiallyLaunchedFromHomeWidget` when the bridge owns delivery. Retaining them creates two dispatch paths. Leave ordinary `ACTION_VIEW` deep links on the existing `duoyi/deep_links` bridge; preserve reminder and OAuth handling ([MainActivity:514–540](/home/ubuntu/duoyi/android/app/src/main/kotlin/com/duoyi/duoyi/MainActivity.kt:514), [main:2677–2700](/home/ubuntu/duoyi/lib/main.dart:2677)).

For Android widget entity links, add the publication's `source=widget`, `widget_day`, `widget_offset`, and `widget_account` to every concrete item URL, using the same fresh-frame requirement as mutating actions ([DuoyiWidgetSnapshot:99–107](/home/ubuntu/duoyi/android/app/src/main/kotlin/com/duoyi/duoyi/DuoyiWidgetSnapshot.kt:99)). Cover Todo, Goal, Note, Diary, Course, Schedule, Calendar, and Anniversary item targets; leave section/tab links as section navigation. After deferred hydration, check captured account generation, auth transition, and the complete binding against the current native publication **before** resolving any entity ID. On mismatch, absent binding, or missing item, open only the correct section. For a widget Intent carrying an old plain entity URL, the native DTO proves it arrived through the widget entry path and requires this safe section fallback. Plain `ACTION_VIEW` URLs from reminders/external clients retain existing detail behavior. Do not merely add query fields to the renderer: the current bound-action branch runs only for `host == action` ([main:4162–4168](/home/ubuntu/duoyi/lib/main.dart:4162)).

## iOS baseline finding and legacy limit

Before the buffered iOS widget bridge, widget URLs entered the app's custom `DuoyiDeepLinkBridge`. The `home_widget` iOS plugin only recognizes URLs with a `homeWidget` query item ([SwiftHomeWidgetPlugin:238–241](/home/ubuntu/.pub-cache/hosted/pub.dev/home_widget-0.7.0+1/ios/Classes/SwiftHomeWidgetPlugin.swift:238)); these widget links do not add that item. The original app bridge had one `pendingInitialLink` slot and could overwrite an early URL, or invoke `onLink` before Dart installed its handler ([DeepLinkService:11–25](/home/ubuntu/duoyi/lib/services/deep_link_service.dart:11)). The current widget-specific bridge addresses those cases for URLs marked `source=widget`. Ordinary external and OAuth URLs still use the single-slot bridge ([AppDelegate:100–159](/home/ubuntu/duoyi/ios/Runner/AppDelegate.swift:100)); their early-delivery limitation remains.

The required iOS item-link follow-up was to carry the same binding fields as mutations and use the same post-hydration entity gate; the current renderer and resolver do so, as reviewed below. Old, cached **plain** iOS widget detail URLs remain indistinguishable from ordinary external/reminder links in the AppDelegate contract. A timeline reload on account change can reduce their lifetime but cannot retroactively bind an already issued URL. A strict guarantee for those old URLs would require changing how all unbound entity deep links route.

## Final implementation review — HEAD `2704add` plus uncommitted diff

**Verdict: accept the Android widget transport and source-marked iOS mutation/entity URL transport at source-review level, within the process-lifetime and 256-pending limits. Plain iOS navigation URLs still use the ordinary deep-link bridge.** The app-owned bridge closes the plugin's mutable-initial-Intent replay path by making Android and iOS `initialLaunchUri()` return null and taking sourced taps from `WidgetLaunchService` ([HomeWidgetService:830–854](/home/ubuntu/duoyi/lib/services/home_widget_service.dart:830)). Android native capture allocates a new UUID for each received Intent and retains at most 256 pending entries, rejecting the newest overflow without evicting accepted taps ([DuoyiWidgetLaunchQueue:10–27](/home/ubuntu/duoyi/android/app/src/main/kotlin/com/duoyi/duoyi/DuoyiWidgetLaunchQueue.kt:10), [DuoyiWidgetLaunchBridge:21–45](/home/ubuntu/duoyi/android/app/src/main/kotlin/com/duoyi/duoyi/DuoyiWidgetLaunchBridge.kt:21)). The pending snapshot and hot callback may overlap; Dart emits only the first instance of an ID, leaves in-flight duplicates unacknowledged, and retries ACK for terminal duplicates ([DuoyiWidgetLaunchBridge:58–70](/home/ubuntu/duoyi/android/app/src/main/kotlin/com/duoyi/duoyi/DuoyiWidgetLaunchBridge.kt:58), [WidgetLaunchService:74–115](/home/ubuntu/duoyi/lib/services/widget_launch_service.dart:74)).

Two real Android widget taps with the same habit URI receive different IDs; the five-second URI filter is bypassed only for an ID already received by the native bridge ([main:3964–3979](/home/ubuntu/duoyi/lib/main.dart:3964), [WidgetLaunchService:28–31](/home/ubuntu/duoyi/lib/services/widget_launch_service.dart:28)). The final-routing set prevents a re-subscribe while hydration is in flight from executing one ID twice ([main:4014–4030](/home/ubuntu/duoyi/lib/main.dart:4014)). `StreamController.broadcast` installs its Dart method handler before native `subscribe`; a pending snapshot and hot callback are deduplicated, and a cancelled subscription rejects old-generation callbacks ([WidgetLaunchService:33–59](/home/ubuntu/duoyi/lib/services/widget_launch_service.dart:33), [WidgetLaunchService:118–131](/home/ubuntu/duoyi/lib/services/widget_launch_service.dart:118)). Both cancel and later subscribe use the same MethodChannel; an arrival while native is unsubscribed remains queued for the next snapshot. The bridge attaches to the Flutter engine rather than Activity recreation, preserving a retained engine's subscription ([DuoyiWidgetLaunchBridge:86–97](/home/ubuntu/duoyi/android/app/src/main/kotlin/com/duoyi/duoyi/DuoyiWidgetLaunchBridge.kt:86), [MainActivity:123–130](/home/ubuntu/duoyi/android/app/src/main/kotlin/com/duoyi/duoyi/MainActivity.kt:123)). This contract is sound for ordinary taps in a live process. An engine/process death between accepted dispatch and native ACK can still replay or lose a mutation; ACK is a delivery handoff, not a storage transaction.

The earlier cap, forged-ID, and malformed URI findings are resolved: the pending-URI cap evicts only non-bridge entries ([main:3937–3952](/home/ubuntu/duoyi/lib/main.dart:3937)); delivery-specific bypass requires an ID owned by `WidgetLaunchService` ([main:3964–3968](/home/ubuntu/duoyi/lib/main.dart:3964), [main:4019–4024](/home/ubuntu/duoyi/lib/main.dart:4019)); native capture rejects opaque/unsupported/oversized URIs and catches malformed query rewriting ([DuoyiWidgetLaunchBridge:16–43](/home/ubuntu/duoyi/android/app/src/main/kotlin/com/duoyi/duoyi/DuoyiWidgetLaunchBridge.kt:16)). Invalid Dart envelopes with a valid ID are terminally ACKed without dispatch ([WidgetLaunchService:74–90](/home/ubuntu/duoyi/lib/services/widget_launch_service.dart:74)). Failed native subscribe or ACK gets a 1/2/4/8/16-second capped backoff drain while subscribed, cancelled on unsubscribe ([WidgetLaunchService:46–72](/home/ubuntu/duoyi/lib/services/widget_launch_service.dart:46), [WidgetLaunchService:104–131](/home/ubuntu/duoyi/lib/services/widget_launch_service.dart:104)). Blank quick-todo and refresh actions remain recoverable while quick-todo with text requires binding ([WidgetLinkDispatch:26–40](/home/ubuntu/duoyi/lib/services/widget_link_dispatch.dart:26)).

Residual scope and operational limits:

- New iOS widget URLs with `source=widget` enter `DuoyiWidgetLaunchBuffer`: each received URL gets a fresh UUID even when its text matches a prior cold or warm URL, duplicate `source`/`widget_delivery` query items are replaced, and up to 256 entries remain pending until ACK ([AppDelegate:11–46](/home/ubuntu/duoyi/ios/Runner/AppDelegate.swift:11)). The bridge snapshots pending entries on `subscribe` and sends hot `onLaunch` callbacks ([AppDelegate:50–93](/home/ubuntu/duoyi/ios/Runner/AppDelegate.swift:50)); `HomeWidgetService` routes iOS to the same Dart delivery-ID service as Android ([HomeWidgetService:830–854](/home/ubuntu/duoyi/lib/services/home_widget_service.dart:830)). Distinct count-habit taps with the same URL therefore bypass the five-second URI filter ([main:3964–3979](/home/ubuntu/duoyi/lib/main.dart:3964)). This is an in-memory handoff: process death and silent newest-entry rejection at capacity can lose a tap.
- `Info.plist` configures a scene delegate and one scene at a time ([Info.plist:40–57](/home/ubuntu/duoyi/ios/Runner/Info.plist:40)). With that manifest present, `AppDelegate` leaves cold URLs to `SceneDelegate` instead of recording a duplicate from `launchOptions` ([AppDelegate:163–179](/home/ubuntu/duoyi/ios/Runner/AppDelegate.swift:163)). `SceneDelegate` forwards every cold `urlContext` and every later open context; the buffer does not merge URLs by text ([SceneDelegate:5–27](/home/ubuntu/duoyi/ios/Runner/SceneDelegate.swift:5), [AppDelegate:21–41](/home/ubuntu/duoyi/ios/Runner/AppDelegate.swift:21)). The OS supplies `urlContexts` as a set, so no receipt order among multiple contexts in one callback is guaranteed. Actual scene lifecycle and device delivery remain unverified.
- Widget bridge `attach` replaces its messenger and resets subscription when a new Flutter engine appears; the new Dart subscription can drain retained widget entries ([AppDelegate:59–84](/home/ubuntu/duoyi/ios/Runner/AppDelegate.swift:59)). `DuoyiDeepLinkBridge.attach` now also tracks messenger identity, replaces its old handler and channel, and guards against stale calls, preserving ordinary external/OAuth channel access after an engine replacement ([AppDelegate:107–139](/home/ubuntu/duoyi/ios/Runner/AppDelegate.swift:107)). Ordinary/OAuth links retain the pre-existing single pending slot and can still lose an early second URL.
- Current iOS whole-widget targets, footer navigation, refresh, and empty quick-todo URLs omit `source=widget`; they use `DuoyiDeepLinkBridge`'s single initial slot rather than the buffered widget queue ([DuoyiWidgets:337–370](/home/ubuntu/duoyi/ios/DuoyiWidgets/DuoyiWidgets.swift:337), [DuoyiWidgets:1585–1619](/home/ubuntu/duoyi/ios/DuoyiWidgets/DuoyiWidgets.swift:1585), [DuoyiWidgets:1951–1979](/home/ubuntu/duoyi/ios/DuoyiWidgets/DuoyiWidgets.swift:1951), [AppDelegate:97–159](/home/ubuntu/duoyi/ios/Runner/AppDelegate.swift:97)). A second early plain navigation URL can overwrite the first. In the reviewed renderer, concrete Todo detail, generic entity rows, and data-mutating action URLs are passed through `actionURL` and receive a binding/source marker; the calendar summary resolves to a section or one of those bound entity hosts ([DuoyiWidgets:652–708](/home/ubuntu/duoyi/ios/DuoyiWidgets/DuoyiWidgets.swift:652), [DuoyiWidgets:1188–1203](/home/ubuntu/duoyi/ios/DuoyiWidgets/DuoyiWidgets.swift:1188), [DuoyiWidgets:1825–1833](/home/ubuntu/duoyi/ios/DuoyiWidgets/DuoyiWidgets.swift:1825), [DuoyiWidgets:2201–2212](/home/ubuntu/duoyi/ios/DuoyiWidgets/DuoyiWidgets.swift:2201)). Published day, UTC offset, and owner epoch isolate stale or other-account widget actions and entities within the local workspace; they do not prove the caller is a widget host or that a specific item was rendered.
